# Vib Ribbon VR: Project Plan

Version 2, 2026-11-18 (session 2). Approved by the owner. Status of every task lives in the tracker: https://claude.ai/artifact/42iBUS2Aiu81652cgnRM1k

Repository: https://github.com/CorrieDivitt/Vib-Ribbon-VR (this file is `docs/PLAN.md` there).

## Goal

A version of Vib-Ribbon playable in VR on PCVR and Meta Quest 3, released free. Primary goals: responsive, consistent timing, and visuals that do justice to the original.

**Scope decisions (2026-11-18):**

- Target hardware is the Quest 3, standalone and as a PCVR headset. Steam Frame is a stretch goal: the architecture must not rule it out, but no work is scheduled for it.
- Generating levels from your own music is a stretch goal. If it cannot be made to work, that does not block a release. The analysis algorithm itself stays in the core, because as far as the decompiled sources read so far show, the six official courses are generated by the same analysis of the official songs.
- Free public release. No code is copied from revib or open-ribbon until their authors say how it may be used; until then we write our own implementation of the behaviour they document.

## Approach in one paragraph

Build a **native VR port**, not a recompilation. A portable C++ game core reproduces the original's logic, using the byte-matching decompilation (revib) as the reading reference. Models, animations, course scripts, sound effects and the six songs are read from the player's own disc image at first run. An emulator running the original disc is the judge: every ported system is tested against captures from it. One OpenXR and Vulkan codebase builds for Windows (PCVR) and Android ARM64 (Quest 3, and later Steam Frame).

## Why this approach fits the goals

| Goal | What the original does | What the native port does with it |
|---|---|---|
| Consistent timing | Gameplay time is the music's sample position. Course scripts, obstacle times and effect windows are all counted in audio samples (22,050 per second, inferred from the disc data). | The audio device clock drives the game. Rendering runs at whatever the headset wants (72 Hz, 90 Hz, 120 Hz or more) and reads the same clock. No 50 Hz frame grid. |
| Responsive input | Input read on the 50 Hz video frame (inferred). | Input timestamped at headset rate and judged in sample time, with a latency calibration tool. |
| Level generation | Onset detection on the audio a short time ahead of what is heard, then pattern selection from the course script. | Same algorithm, same fixed-point arithmetic, run on the decoded file. Because the whole file is available, the course is deterministic and testable. |
| Beautiful visuals | About 6,500 line primitives in the main game archive, a few hundred on screen, drawn as 1-pixel lines at 288 lines of resolution. | The same line data drawn as anti-aliased, resolution-independent lines with glow, in real stereo depth. The models carry real 3D coordinates and the animations are per-object rotation, scale and position keys, so they hold up from a moving viewpoint. |
| Platforms | PS1 only. | One codebase: Windows x64 for PCVR, Android ARM64 for Quest 3. The same Android build is the first thing to try on Steam Frame, which Valve documents as running Android APKs and native Linux ARM64. |

## Architecture

```
            +--------------------- vibcore (portable C++, no graphics) ---------------------+
 disc.cue   |  ingest: CUE/BIN, ISO9660, PAK      formats: TMD ANM ANC FSL VH/VB TIM        |
 music file |  audio front end (22.05 kHz mono blocks)  ->  onset detection, peak picking   |
            |  course script (FSL) + RNG  ->  parts timeline  ->  gameplay rules, scoring   |
            |  scene description out: line models, transforms, camera, meters, messages     |
            +--------------------------------------------------------------------------------+
                         |                                   ^
                         v                                   | sample clock, timestamped input
            +---------------------- platform layer ----------------------+
            |  render: Vulkan line renderer (flat window and stereo)     |
            |  xr: OpenXR session, tracking, controllers, haptics        |
            |  audio: low-latency output with position query             |
            |  targets: Windows x64, Android ARM64                       |
            +-------------------------------------------------------------+

 Reference rig (tools only, never shipped): emulator + debugger + revib symbols -> golden event files
```

Rules that keep Steam Frame possible without scheduling it:

1. vibcore has no platform, graphics or audio-device code.
2. Input goes through OpenXR interaction profiles, never a vendor SDK.
3. The Android build uses the standard Khronos OpenXR loader.
4. No dependency that exists only for x86.

Rules that keep the timing honest:

1. The core never reads a frame counter. Its only clock is the audio sample position.
2. The core is deterministic: same audio, same course script, same seed, same inputs give the same result. This is what makes golden tests possible.
3. Rendering interpolates. Animation clips carry their own rate in their header (10, 15, 20, 30 or 60 on this disc, to be confirmed as frames per second) and are sampled by time.

## Stack

- Language and build: C++20, CMake, Ninja. Dependencies fetched by CMake.
- XR: OpenXR (Khronos loader on Windows, the headset vendor's loader on Android).
- Graphics: Vulkan on every target. Lines drawn as expanded quads with analytic anti-aliasing. Glow built from additive geometry rather than full-screen blur so it stays cheap on Quest.
- Audio: one thin interface over WASAPI (Windows) and AAudio (Android), both through a small single-file library, with output-position queries for the clock.
- Decoding the player's music (stretch goal S.1): public-domain single-file decoders for MP3, FLAC, OGG and WAV.
- Desktop shell for development: SDL3 window, gamepad and keyboard.
- Tests: golden files generated by the reference rig on the developer's PC. The repository contains no game data.

Alternatives considered and set aside:

- **Fork vib-ribbon-recomp and add OpenXR.** Quickest way to see the original in a headset on PC, following the Medal of Honor VR recomps. Rejected as the base because it cannot meet the timing, visual or standalone goals. Details in the handoff document, section 5.
- **Compile the decompilation directly against a PsyQ replacement (Psy-Z or PsyCross).** Keeps original code verbatim, but the rendering path would be rewritten anyway to get real 3D lines, and the licence position is the same as adapting the code. Still an option for the reference rig.
- **A general engine (Godot, Unity, Unreal).** Faster menus and XR setup, weaker control over audio latency, far more engine than a line-drawing game needs. Godot stays as the fallback if task 1.8 shows the custom stereo path is too costly.

## Phases

Each phase ends with something you can run and judge.

### Phase 0. Research and architecture (done, pending your sign-off)

Outputs: this plan, the tracker, the handoff document, the extracted disc in `research\extracted`, three Python research tools in `tools\research`. Signed off 2026-11-18.

### Phase 1. Foundations

Goal: repo, toolchain, asset pipeline, a trustworthy reference, and proof that one codebase draws lines in stereo on PC and Quest 3.

Progress: 1.1 done (repo skeleton with CMake presets, tests and CI). 1.3 under way (C++ CUE, raw sector, ISO 9660 and PAK readers plus `vibtool`, tested against the disc).

1.1 Repository skeleton. 1.2 Windows toolchain. 1.3 Disc ingest library and CLI. 1.4 Format loaders. 1.5 Desktop asset viewer. 1.6 Reference capture rig. 1.7 Read the decompilation and write the behaviour spec. 1.8 Stereo spike on PCVR and Quest 3. 1.9 Ask revib's author how the decompilation may be used.

Done when: any model and animation from the disc plays in the viewer, a stereo test scene runs on PCVR and Quest 3, and reference event lists exist for all six songs.

### Phase 2. Game core, headless

Goal: the whole game as a deterministic library with no graphics.

2.1 Audio front end. 2.2 Onset detection and peak picking. 2.3 Course script interpreter and RNG. 2.4 Gameplay rules. 2.5 Golden tests. 2.6 Demo mode. 2.7 High scores and options.

Done when: event lists match the reference for all six songs, and unit tests run without game data.

### Phase 3. Flat desktop build

Goal: prove the game is right on a monitor first.

3.1 Line renderer. 3.2 Scene. 3.3 Audio output and clock. 3.4 Input. 3.5 Title and menus. 3.6 Side-by-side comparison with the emulator.

Done when: all six songs are playable start to finish on desktop and match the original.

### Phase 4. PCVR

Goal: the full game in a headset.

4.1 OpenXR session, stereo, controllers, haptics. 4.2 VR staging. 4.3 Line quality in the headset. 4.4 In-world menus. 4.5 VR timing and calibration.

Staging direction for 4.2, to be prototyped rather than decided on paper: the ribbon as a world-locked diorama in front of the player; the original camera moves reinterpreted as motion of the diorama with a comfort setting; an optional classic mode that shows the original framing on a large virtual screen; passthrough on Quest 3 so the ribbon runs through your room.

Done when: the complete game is playable through Quest Link, SteamVR and Virtual Desktop at headset refresh rate.

### Phase 5. Standalone Quest 3

5.1 Android ARM64 build. 5.2 Disc image import on the headset. 5.3 Low-latency Android audio and calibration. 5.4 Performance and passthrough.

Done when: the standalone build holds 90 Hz or better with timing equal to PCVR.

### Phase 6. Polish and release

6.1 Visual and haptic polish, comfort and accessibility. 6.2 Packaging and first-run disc import. 6.3 Credits and licence notices. 6.4 Test matrix and release.

### Stretch goals (none block a release)

- S.1 Levels from your own music: file picker, decoders, the original analysis run on any track. Cheap once Phase 2 works, since the official songs use the same analysis.
- S.2 Music import on the Quest 3.
- S.3 Steam Frame: run the Quest APK, evaluate a native Linux ARM64 build, controller profile.

## Risks

See the tracker for the live list. The three that could change the plan:

1. **Licence of the decompilation.** revib has no licence. Plan: ask its author (task 1.9); meanwhile we write our own code from the behaviour spec in task 1.7 and copy nothing. The architecture is the same either way.
2. **Bit-exact analysis.** The PS1 analyzes audio captured through its sound chip. If our decoded samples differ from that capture, obstacles shift. The golden tests in 2.5 are designed to catch this early.
3. **Custom stereo renderer cost.** Task 1.8 tests it in Phase 1. Fallback is Godot with the core as a native extension.
